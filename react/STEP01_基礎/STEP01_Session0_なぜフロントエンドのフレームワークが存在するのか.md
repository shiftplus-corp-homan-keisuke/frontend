## 📜 ウェブ開発の歴史：サーバーサイドレンダリングの時代

### 2010 年以前：すべてはサーバーで作られていた

2010 年以前は、すべてのウェブサイトは常にサーバー上でレンダリングされていました。

サーバーサイドレンダリングでは、ウェブサイトは基本的にバックエンドで組み立てられます。ウェブサーバー上で、データとテンプレートに基づいて完成された HTML、CSS、JavaScript のコードが、クライアントサイド（つまりページを要求したウェブブラウザ）に送られます。ブラウザはこのコードを受け取り、基本的にそれを画面に描画します。

サーバーサイドでレンダリングされたウェブサイトの典型的な例は、WordPress で構築されたすべてのウェブサイトです。

![alt text](images/STEP01_Session0_なぜフロントエンドのフレームワークが存在するのか/image.png)

### 当時の JavaScript の役割

このようなウェブサイトに含まれていた JavaScript は、当初は簡単なアニメーションやホバー効果など、ページに簡単なダイナミクスを加えるためだけのものでした。そして通常、jQuery と呼ばれる当時大人気だったライブラリがこのために使われました。なぜなら、当時はどのブラウザでも JavaScript がまったく同じように動作しなかったからです。もちろん、あなたもすでにこのような API と接したことがあると思います。

```javascript
// 2010年頃の典型的なjQueryコード
$(document).ready(function () {
  $(".button").hover(
    function () {
      $(this).addClass("highlight");
    },
    function () {
      $(this).removeClass("highlight");
    }
  );

  $(".menu-toggle").click(function () {
    $(".menu").slideToggle();
  });
});
```

## 🌐 変化の波：シングルページアプリケーションの台頭

### JavaScript の進化と新しい課題

しかし時が経つにつれ、開発者はブラウザで実行される JavaScript コードをどんどん書くようになり、いつしか本格的なウェブアプリケーションとなり、いわゆる**シングルページアプリケーション（SPA）**が台頭するようになりました。

これらは基本的にサーバーではなくクライアントでレンダリングされるウェブページです。つまり、クライアントサイドレンダリングでは、基本的にウェブページをレンダリングする作業はサーバーからクライアントに移されました。

### 現代のウェブアプリケーション

現在、これらをウェブページとは呼ばず、**ウェブアプリケーション**と呼ぶようになりました。

現在、ウェブアプリケーションは依然としてデータを必要としており、それは通常**API**という形でバックエンドから来ます。そのため、アプリケーションはこの API データを消費し、アプリケーションのビューごとに画面をレンダリングします。

これらのシングルページアプリケーションは、基本的にネイティブのデスクトップアプリケーションや電話アプリケーションを使っているかのように感じられます。そのため、ページをリロードすることなく、リンクをクリックしたり、フォームを送信したりすることができます。技術的には常に同じページにいることになり、**シングルページアプリ**と呼ばれる理由がここにあります。

![alt text](images/STEP01_Session0_なぜフロントエンドのフレームワークが存在するのか/image-1.png)

### サーバーサイドレンダリングの復活

ここで触れておきたいのは、サーバーサイドレンダリングが再び重要性を増しているという点です。Next.js や Remix など、クライアントサイドレンダリングで培われた概念の上に新しい仕組みを統合したメタフレームワークが登場したことで、SSR は現代的な形に再定義されています。

しかし、いずれにせよ、シングルページアプリケーションの作り方を学ぶ必要があることに変わりはありませんが、もちろんバニラ JavaScript でそれを行いたいでしょうか？

実際には、そうしたくはありません。なぜなら、大規模なアプリケーションを構築するためにバニラ JavaScript を使用することには、実際にいくつかの問題があるからです。すぐにお見せしますが、まず、フロントエンドアプリケーションの構築とは、実際にはデータを処理し、そのデータを美しいユーザーインターフェイスで表示することがすべてだということを確認しておきましょう。

## 💭 フロントエンド開発の本質：データと UI の同期

### フロントエンド開発とは何か

フロントエンドアプリケーションの構築とは、**データを処理し、そのデータを美しいユーザーインターフェイスで表示すること**がすべてです。

考えてみれば、ウェブアプリケーションがすることは基本的にそれだけです。データを受信し、ユーザーがアプリを使用するたびにデータを変更し、常に現在のデータを画面に表示する。

### 最も重要で困難な課題

これは何を意味するかというと、シングルページアプリ、そしてあらゆるアプリケーションやウェブサイトにおいて最も重要なタスクは、**ユーザーインターフェイスをデータと同期させ続けること**、言い換えれば、**UI が常にデータの現在の状態を表示するようにすること**です。

結局のところ、正しいデータを表示し、それが長期にわたって正しいままであることを確認することは、解決するのが本当に難しい問題なのです。

### 現実世界の例：Airbnb アプリケーション

その理由を理解するために、この Airbnb のアプリケーションを見てみましょう。

https://www.airbnb.jp/

このインターフェイスでは、いくつものデータを確認することができます：

- アパートのリスト
- 検索バー
- 適用されているフィルター（に関するデータ）
- ユーザーが地図を移動したときに検索結果を更新するかどうかを示すデータ

これらはすべて、アプリが依存しているデータです。そして実際に現実世界の Airbnb のアプリケーションには、非常に多くのデータがあります。

実際、ここにあるリストでさえ、すべてではありません。

**複雑な相互依存関係**

私たちが知っているように、これらのデータはすべて、ユーザーインターフェースと常に同期している必要があり、また他のデータとも同期している必要があります。なぜなら、これらはすべて相互に関連しているからです。

例えば：

- 場所や日付のデータを変更した場合、UI は新しい日付を表示し、アパートのリストも更新する必要があります
- 地図にアパートの場所を示す必要があるため、アパートが変われば地図も変わらなければなりません
- 地図が移動されると、アパートのリストも変更されるはずです（ただし、ユーザーが以前に緑のチェックボックスをクリックした場合に限る）

そのため、これらのデータの断片はさらに相互に関連しており、本当に混乱する可能性があります。

### ステート（状態）という概念

現実世界のアプリでは、これらのデータの断片をそれぞれ**ステート（状態）**と呼びます。

これらの例に基づけば、**フレームワークなしでは、この超複雑な UI とこの膨大な量のデータを同期させ続けることは事実上不可能**だと言えます。

## 🚫 バニラ JavaScript の限界

### なぜバニラ JavaScript では困難なのか

バニラ JavaScript でこのようなものを作るのがなぜそんなに難しいのでしょうか？

それでも、なぜなのか疑問に思うかもしれません。なぜバニラ JavaScript でこのようなものを構築するのがそんなに困難なのでしょうか？

それは 2 つの大きな側面に集約されます。

### 問題 1：直接的な DOM 操作の複雑さ

第一に、バニラ JavaScript だけで複雑なフロントエンドを構築するには、**大量の DOM の横断と操作を直接行う必要がある**ことです。

```javascript
// バニラJavaScriptでの典型的なDOM操作
const counterElement = document.getElementById("counter");
const incrementButton = document.getElementById("increment-btn");
const decrementButton = document.getElementById("decrement-btn");
const resetButton = document.getElementById("reset-btn");
const messageElement = document.getElementById("message");

let count = 0;

function updateUI() {
  counterElement.textContent = count;

  // 複雑な条件分岐
  if (count > 10) {
    counterElement.style.color = "red";
    messageElement.textContent = "高い値です！";
    messageElement.style.display = "block";
  } else if (count < 0) {
    counterElement.style.color = "blue";
    messageElement.textContent = "負の値です";
    messageElement.style.display = "block";
  } else {
    counterElement.style.color = "black";
    messageElement.style.display = "none";
  }

  // ボタンの状態管理
  decrementButton.disabled = count <= 0;
  incrementButton.disabled = count >= 20;
}

incrementButton.addEventListener("click", () => {
  count++;
  updateUI();
});

decrementButton.addEventListener("click", () => {
  count--;
  updateUI();
});

resetButton.addEventListener("click", () => {
  count = 0;
  updateUI();
});

// 初期化
updateUI();
```

このように、手動での要素選択、クラスの切り替え、DOM のトラバース、テキストやスタイル操作などをすべて自前で記述する方法は、Airbnb のような規模では確実に破綻します。コードは指数関数的に複雑化し、スパゲッティ化が避けられません。

これが第一の問題です。

### 問題 2：ステートの分散管理

2 つ目の大きな問題は、典型的なバニラ JavaScript アプリでは、**単純なテキストや数字などの状態が、しばしば DOM にそのまま格納されてしまう**ことです。

つまり、アプリケーションの中心的な場所ではなく、HTML 要素そのものにあるのです。

```javascript
// 悪い例：状態がDOMに分散している
function getCurrentCount() {
  return parseInt(document.getElementById("counter").textContent);
}

function isMessageVisible() {
  return document.getElementById("message").style.display !== "none";
}

function updateCounterFromInput() {
  const inputValue = document.getElementById("counter-input").value;
  const currentCount = getCurrentCount();

  // 状態がDOMの各所に散らばっているため、同期が困難
  if (inputValue !== currentCount.toString()) {
    document.getElementById("counter").textContent = inputValue;
    // 他のすべての関連要素も更新する必要がある...
  }
}
```

その結果、アプリの多くの部分が DOM の状態に直接アクセスして変更することになり、スパゲッティコードはさらに理解しづらくなります。さらに悪いことに、アプリケーションに多くのバグをもたらすことになります。

そして、誰もバグは欲しくないですよね？

### 自力解決の困難さ

もちろん、これらの問題を自力で解決しようとすることも可能ですが、その場合、独自のフレームワークを作ることになり、すでに存在する確立されたフレームワークよりもずっと悪いものになる可能性が高いです。

だから現時点では、React のような戦場でテストされたフレームワークを使ったほうがいいのです。

さて、では、JavaScript だけでシングルページのアプリを書くのが難しい理由がわかったところで、冒頭で質問した基本的な質問に答えることができます。

## ✨ フロントエンドフレームワークが存在する理由

### 根本的な理由

JavaScript だけでシングルページのアプリを書くのが難しい理由がわかったところで、冒頭で質問した基本的な質問に答えましょう。

**では、なぜフロントエンドフレームワークが実際に存在するのでしょうか？**

ここまでの内容で既に答えの大部分は見えてきたはずです。

このようなフレームワークが存在する大きな基本的な理由は、**ユーザーインターフェイスをデータと同期させ続けることが本当に難しく、そして多くの作業でもあるから**です。

### フレームワークが提供する価値

基本的に、Angular、React、Vue のようなフレームワークは、**データをユーザーインターフェースと同期させるという困難な作業を、私たち開発者から取り除いてくれる**のです。

彼らはこの本当に困難な問題を解決してくれるので、開発者はデータ自体とユーザーインターフェース自体の構築だけに集中することができます。

さて、異なるフレームワークがこれを行う異なるアプローチを持っていますが、それらはすべて UI とデータを時間の経過とともに同期させるという事実において似ています。

### 構造化されたコードの強制

フレームワークが与えてくれるもうひとつの非常に貴重なものは、**基本的に正しいコードの構造化と記述方法を強制してくれること**です。

本質的には、これらのフレームワークの作者たちは、アプリケーションを構造化する優れた方法を考え出したのであり、他の開発者たちも同様にこれらの規約に従うことで、うまくいけばスパゲッティコードを大幅に減らしてより良いアプリケーションを構築することができます。

### チーム開発における一貫性

最後に、フレームワークは開発者、特にチームにウェブアプリケーションを構築する一貫した方法を提供します。

こうすることで、チームの全員が他の全員と同じスタイルでアプリのパートを構築することになり、最終的にはより一貫性のあるコードベースと製品を作ることができます。

**これが、現代のウェブ開発が JavaScript フレームワーク中心になっている根本理由です。**

## 🚀 React 概要：React とは何か

ここまでで、そもそもなぜ JavaScript フレームワークが必要なのかを理解できました。では、最も広く使われているフレームワーク（ライブラリ）である **React** について学び始めましょう。

このセクションでは、React が実際に「何で」「どのように動作するのか」を、高い視点から整理します。ぎゅっと詰まった内容ですが、今後の土台になるとても重要な観点です。

### 🔖 公式定義と少し踏み込んだ定義

公式ドキュメントでは次のように説明されています：

> React はユーザーインターフェイスを構築するための JavaScript ライブラリです。

…悪くはないですが、これだけだと「で、何が特徴なの？」となりますよね。そこで、ここでは少し拡張した定義で捉えます：

> React とは、**非常に人気が高い / 宣言的 (Declarative) / コンポーネントベース / ステート駆動 / ユーザーインターフェイス構築のための JavaScript ライブラリ（Facebook=Meta によって作成）** である。

この一文を分解していくことで、React の本質を段階的に理解できます。

### 🧱 コンポーネントベース (Component-Based)

React は **コンポーネント** の集合体として UI を構築します。ボタン、入力欄、検索バー、カード、ナビゲーション……こうした UI の部品ひとつひとつがコンポーネントです。

React がしていることを乱暴にまとめると：

> 「コンポーネントを受け取り、それを組み合わせてブラウザ上に描画する」

複雑な UI（例：Airbnb のような画面）は、小さなコンポーネントを **レゴブロックのように組み合わせ・入れ子にし・再利用して** 形作られます。

再利用の典型例：

- 物件一覧 = 同じ「ListingCard」コンポーネントを異なるデータで複数回描画
- 共通ボタン / フォームフィールド / レイアウト枠 などを全体で再利用

#### 🧩 コンポーネント構成イメージ（階層）

```
<App>

    <Header>
      <Logo />
      <GlobalSearchBar />
      <UserMenu />
    </Header>
    <Main>
      <SearchFiltersPanel>

      </SearchFiltersPanel>
```

### 🗣 宣言的 (Declarative) と JSX

React の UI 記述は **JSX** という構文で行います。JSX は _JavaScript + (見た目は) HTML_ を組み合わせた構文で、他コンポーネントの埋め込みや式展開、条件分岐を自然に書けます。

宣言的とは：

> 「どう DOM を逐次操作するか (命令型)」ではなく、「現在の状態 (state) に対して UI はこうあるべき、と宣言する」こと。

つまり：

- バニラ JS: DOM を取得して、クラス外して、追加して… と逐次命令
- React: `return (<ListingCard featured={isHot} />)` と _最終形_ を宣言

React は DOM を直接触らせず、**抽象化レイヤ** を提供します。「何を表示したいか」だけを表現し、「どう効率的に更新するか」は React 本体（後述の Virtual DOM / Fiber など）が担当します。

簡単な例：

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <div className="counter">
      <p>現在値: {count}</p>
      <button onClick={() => setCount(count + 1)}>＋1</button>
    </div>
  );
}
```

ここでは「状態がこうなら UI はこう」と宣言しているだけで、`count` が変わったあとの DOM 差分適用ロジックは書いていません。

#### 🆚 命令的 vs 宣言的 比較表

| 観点             | 命令的（Imperative: jQuery/バニラ） | 宣言的（Declarative: React） |
| ---------------- | ----------------------------------- | ---------------------------- |
| 思考単位         | 「手順」(どうやるか)                | 「最終形」(何であるべきか)   |
| DOM への関与     | 直接取得・操作                      | 抽象化（仮想 DOM / Fiber）   |
| 状態変化         | 手動で同期（class 追加/削除等）     | state を更新すると自動反映   |
| レンダリング粒度 | 自分で必要箇所を決める              | React が差分計算             |
| 学習初期負荷     | 低め（直感的）                      | やや高い（概念習得必要）     |
| 規模拡大時の保守 | 複雑化しがち                        | 構造化されやすい             |

#### 簡易コード比較

命令的（変更点を逐次指示）:

```js
// ボタンをクリックするたびに手動で DOM 更新
btn.addEventListener("click", () => {
  count++;
  span.textContent = count;
  if (count > 10) span.classList.add("warn");
  else span.classList.remove("warn");
});
```

宣言的（状態 -> UI マッピング）:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button
      className={count > 10 ? "warn" : ""}
      onClick={() => setCount((c) => c + 1)}
    >
      {count}
    </button>
  );
}
```

> 宣言的アプローチは「現在の state が UI の唯一の真実」であることを保証し、同期ミスを減らします。

### 🔄 ステート駆動 (State-Driven) と再レンダリング

React の中心概念は **state（状態）** です。state が UI の「ソース・オブ・トゥルース (単一の信頼できる源)」。

レンダリングの流れ（超シンプル化）：

1. 初期 state を使ってコンポーネントを描画
2. ユーザー操作 / API レスポンスなどで state が変化
3. React がその変更を検出し、差分を計算
4. 変更が必要な部分だけ DOM を更新（再レンダリング）

> React は **state の変化に“反応 (react)” して UI を更新する** — これが名前の由来です。

例：Airbnb の「物件一覧 state」が API で増える → 新しいリストアイテムが自動で表示される。

#### 🔁 状態更新ライフサイクル（概念フロー）

| ステップ              | 役割             | 注意点                     | 例                 |
| --------------------- | ---------------- | -------------------------- | ------------------ |
| 1. イベント           | ユーザー操作発火 | 同期/非同期両方あり        | onClick / onChange |
| 2. setState 呼び出し  | 更新予約         | バッチングされる可能性     | setCount(c=>c+1)   |
| 3. 再レンダリング判定 | shouldUpdate?    | メモ化や比較が関与         | React 内部         |
| 4. 仮想 DOM 再構築    | 新ツリー生成     | 副作用はここでは起こさない | render phase       |
| 5. Diff               | 旧ツリー比較     | key の設計が効く           | key=...            |
| 6. DOM パッチ         | 必要最小限更新   | 大量更新を抑制             | 実 DOM mutate      |
| 7. 画面反映           | UI 一貫性        | レイアウト/ペイント発生    | ブラウザ           |

> 詳細な Fiber のスケジューリング（中断・再開等）は後続セッションで扱います。

### 🧩 ライブラリ vs フレームワーク

React は厳密には **フレームワークではなく「ビュー層ライブラリ」** です。つまり「UI をどう描くか」に特化していて、以下のような領域は含まれていません：

- ルーティング（画面遷移）
- データ取得戦略（キャッシング / フェッチ）
- ビルド最適化 / SSR / SSG などの統合

そのため、実際のプロダクション開発では追加ライブラリを組み合わせる必要があります（例：React Router, TanStack Query など）。

これを包括的に補うメタフレームワークとして **Next.js / Remix / Gatsby** などが存在します（これらは SSR / SSG / ルーティング / 最適化を統合）。

ここではまず「純粋な React のメンタルモデル」を確立し、その後に周辺エコシステムへ進みます。

#### 📊 比較表：React と代表的メタフレームワーク

| 項目         | React 本体                | Next.js                                 | Remix                            | 備考                         |
| ------------ | ------------------------- | --------------------------------------- | -------------------------------- | ---------------------------- |
| 提供範囲     | View レイヤ               | SSR/SSG, ルーティング, 画像最適化       | サーバーアクション, ルーティング | React を内包                 |
| データ取得   | 自前実装 / ライブラリ選択 | fetch + Route Handlers / Server Actions | loader / action                  | アーキテクチャ思想が異なる   |
| ルーティング | なし                      | ファイルシステムベース                  | ファイル + ネスト                | 両者ともレイアウト構造を表現 |
| 静的生成     | 直接は不可                | SSG/ISR 標準                            | 対応（Remix v2+）                | 配信最適化                   |
| 画像最適化   | なし                      | `<Image />`                             | 一部外部連携                     | CDN と連携                   |
| Edge 対応    | 任意                      | 対応拡大中                              | 対応                             | 実行環境差異考慮             |
| 学習曲線     | 低〜中（概念理解必須）    | 中（フレームワーク規約追加）            | 中（Web Standard 志向）          | 目的で選定                   |

> まずは「React 単体の挙動」を理解してからメタフレームワークへ進むと混乱が少ないです。

### 🌍 圧倒的な普及とエコシステム

React を選ぶ大きな理由のひとつは「**圧倒的な採用実績とコミュニティ規模**」。

影響：

- npm 週次ダウンロード数はフロントエンド UI ライブラリの中でも最大級
- 大企業（Meta, Netflix, Airbnb, Uber など）が長期採用 → 中小企業も追随
- 求人数が多く、報酬水準も比較的高め
- Stack Overflow / GitHub / Qiita / Zenn などで情報が豊富
- 無数のサードパーティライブラリ（UI キット, 状態管理, 可視化, フォーム, 国際化…）

この巨大な「知識とコードの資産」を活かせること自体が、React の最大の価値のひとつです。

| サーバー状態           | TanStack Query / SWR                               | API フェッチ + キャッシュ   | データ鮮度 / キャッシュ戦略 |

### 🧠 React が特に「得意なこと」まとめ

1. **現在の state に基づきコンポーネントツリーを宣言し、UI を描画すること**
2. **state 変化に “反応” して UI を最新の状態へ同期し続けること**

これを支える内部メカニズム（キーワードだけ先取り）：

- Virtual DOM / Diffing
- Fiber アーキテクチャ（協調的レンダリング）
- 単方向データフロー（データは上 → 下へ）
- コンポーネント分割と props
- フック（Hooks）によるロジック再利用

これらは今後のセッションでじっくり掘り下げていきます。

#### 📝 チートシート（今覚える最小セット）

| 用語              | 一言要約                     | もう一歩踏み込むと                 | 後で深掘り                   |
| ----------------- | ---------------------------- | ---------------------------------- | ---------------------------- |
| Component         | UI の再利用単位              | Props と state を入力に UI を出力  | ライフサイクル最適化         |
| JSX               | 宣言的 UI 記述構文           | Babel が createElement に変換      | 型付け (TSX)                 |
| State             | 変わるデータ                 | 変わると再レンダリングを引き起こす | バッチング / 同期タイミング  |
| Props             | 親 → 子の入力                | 不変（子は書き換えない）           | Prop drilling / Context      |
| Virtual DOM       | 中間表現                     | 差分計算で最小 DOM 更新            | Fiber により分割処理         |
| Fiber             | レンダリングエンジン内部構造 | 中断再開/優先度制御                | 並行レンダリング             |
| One-way Data Flow | データは上 → 下              | 予測可能性向上                     | 双方向が必要なら制御パターン |
| Hooks             | 状態/副作用 API              | 関数コンポ間でロジック共有         | カスタム Hook 設計           |

> わからない単語があっても OK。配置を俯瞰できれば十分なスタートラインです。

### 学んだ核心

1. 歴史的推移：SSR 全盛 → SPA 台頭 → SSR/CSR ハイブリッド再評価
2. 本質課題：UI と複雑化する状態（ステート）を一貫して同期し続けること
3. バニラ JS の限界：命令的 DOM 更新 + 状態散乱 + 保守性崩壊
4. フレームワークの役割：宣言的・コンポーネント・単方向データフローで複雑性を吸収
5. React の位置付け：ビュー層ライブラリとして「状態 →UI 写像」に特化し、周辺はエコシステムに委譲

### なぜフレームワークが不可欠か（要約）

| 課題領域   | バニラ JS の現実   | フレームワークの抽象化     | 成果     |
| ---------- | ------------------ | -------------------------- | -------- |
| DOM 更新   | 手続き・漏れやすい | 仮想 DOM / 差分適用        | 一貫性   |
| 状態配置   | DOM/グローバル散乱 | コンポーネント境界 + props | 予測可能 |
| 再利用     | コピペ / ad-hoc    | コンポーネント合成         | DRY      |
| チーム開発 | 流儀バラバラ       | 規約 & 心的モデル共有      | 保守性   |
| スケール   | 複雑性爆発         | 階層化 + 単方向データ流    | 制御可能 |
