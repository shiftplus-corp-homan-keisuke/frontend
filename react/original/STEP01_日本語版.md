
# セクション概要

このセッションでは、Reactアプリを構築する3つの核となる概念を探求していきます。コンポーネント、props、そしてJSXです。

コンポーネントがReactアプリケーションの構成要素であることを学び、強力なJSX構文を使用してコンポーネントを作成し、再利用する方法を学びます。

また、propsを使用してコンポーネント間でデータを共有し、リストのレンダリング、条件付きレンダリングなどについて学びます。この最初の美しいプロジェクトを構築しながら、すべてを学んでいきます。

その過程で、これらの基本的なスキルを使用して開発者プロフィールカードを構築することで、Reactを自分で練習し始めることになります。

それでは、今すぐこのReactの旅を始めましょう。

# ルートコンポーネントのレンダリングとStrictモード

このセッション全体を通して構築していくPizza Menuプロジェクトへようこそ。

この講義では、実際にこのプロジェクトを完全にゼロから構築し始めたいと思います。完全にゼロからというのは、ここにある本当に必要のないファイルをすべて削除して、プロジェクトをゼロから始めるということです。

では、これらのファイルを閉じて削除し、ゼロから始めましょう。

最初のエラーが発生しました。ブラウザを片側に配置し、コードエディタを左側に配置したことに注目してください。これにより、常に出力を同時に見ることができます。

アプリケーションがindex.jsファイルを探しているのがわかりますが、もちろんそれはもう存在しません。削除したからです。

では、ゼロから始めましょう。このフォルダ内に最初のファイルを作成します。それはindex.jsと呼ばれ、本当にindex.jsと呼ばれる必要があります。なぜなら、このプロジェクトのモジュールバンドラーであるwebpackは、エントリーポイントがindex.jsと呼ばれることを期待しているからです。

それでは、Reactをインポートすることから始めましょう。

```javascript
import React from 'react';
```

これは単純なJavaScriptです。モジュールのインポートはJavaScriptの一部で、特にES6以降のものです。

次に、ReactDOMもインポートしましょう。

```javascript
import ReactDOM from "react-dom/client";
```

これらの2つのライブラリをインポートしました。pure Reactの講義で基本的に同じ2つのライブラリをインポートしたことを覚えているでしょう。

実際、そのファイルを開いて比較してみましょう。デスクトップのpure React、そしてindex.HTMLを開きます。ここでもReactとReactdomをインポートしていますが、これらのスクリプトタグを使用しています。

しかし、ここではNPMを使用してインストールされており、JavaScriptから直接来るインポート構文を使用してプロジェクトにインポートしています。

次に、実際にAppコンポーネントを再び作成しましょう。

```javascript
function App() {
  return <h1>Hello React!</h1>;
}
```

Appと呼ばれる必要はありません。これは単なる慣例です。必要なのは、このコンポーネントが大文字で始まることです。

今度は、これをDOMにレンダリングする必要があります。これは以前に行ったことと似ています。

もちろん、将来的にはこれらすべてを手で書くことはありませんが、少なくとも一度は手で書いて、Reactアプリケーションの初期化プロセスで何が起こっているかを実際に知ってもらいたいと思います。

では、いわゆるrootを作成しましょう。そのためにReactDOMライブラリを使用し、そこにcreateRootメソッドがあります。

```javascript
const root = ReactDOM.createRoot(document.getElementById("root"));
```

このroot要素を選択します。publicフォルダにあります。ここにはこの奇妙なURLなどがありますが、webpackがこれらすべてを処理します。

私たちが探しているのは、このidを持つdivです。id="root"です。Reactがこのdiv内にアプリケーションをレンダリングできるように、この要素を選択します。

```javascript
root.render(<App />);
```

これで完了です。Hello React!が表示されます。これが私たちの素敵なappコンポーネントです。

これが基本的にReactをゼロから書く方法です。

これがReact version 18でrootをレンダリングする方法、つまり基本的にアプリをDOMにレンダリングする方法であることに注意を向けたいと思います。

しかし、React 18以前の古いコードベースを見ている場合、これは異なる方法で動作していました。少し違って見えました。

React 18以前では、単純にReact.renderを行い、そこにアプリを配置していました。また、別の変更として、これを取り除く必要がありました。

これはReact 17アプリでしたが、これらの変更により、react-dom/clientを持ち、この方法でレンダリングすることで、アプリをReact 18に対応させました。

最後に、ここで話したいのはstrict modeです。アプリコンポーネントをルートコンポーネントとして直接レンダリングする代わりに、これをstrict modeコンポーネントでラップすることで、strict modeを簡単に有効にできます。

```javascript
root.render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
);
```

このstrict modeは基本的にReactの一部であるコンポーネントで、Reactから取得できます。

strict modeは大したことではありません。開発中にすべてのコンポーネントを2回レンダリングして特定のバグを見つけるだけです。また、Reactは古いReact APIの部分を使用しているかどうかもチェックします。

strict modeは画期的なものではありませんが、Reactアプリケーションを開発する際には常に有効にするのが良いアイデアです。

# コーディングを始める前に：デバッグ

これから、あなたは自分のコンピューターでコーディングを始めることになり、エラーが発生し、いくつかのことが単純に動作しないことはほぼ確実です。

そこで、最初から、これらのエラーや問題に対処するためのいくつかのテクニックを紹介したいと思います。これは本当に重要な講義なので、スキップしないでください。

コードで何かを変更して保存し、出力を見たいとしましょう。しかし、何らかの理由で、ページがブラウザで更新されなかったと想像してください。どうしますか？

それが起こったときは、パニックにならず、代わりに、今お伝えするいくつかの解決策を試してください。

最初の解決策は、アプリケーションが実際に実行されていることを確認することです。信じられないかもしれませんが、これは実際に私にも起こったことがあります。アプリが実行されているはずだと思い、コードを更新し、何かを変更していましたが、アプリがリロードされない理由がわかりませんでした。

ある時点で、実際にはアプリを開始していなかったことに気づきました。これは実際に起こりうることです。

アプリが実行されていない場合、つまり以前に示した「npm start」を使用していない場合、もちろんアプリはブラウザでリロードできません。

しかし、実際に実行されているが、まだ更新されていない場合は、アプリを停止して再起動することが解決策の1つになります。

ターミナルでアプリが現在実行されているタブがここにあります。停止するには、Control + Cを使用します。Macでは、Control + C、Windowsでも単にControl + Cです。

Windowsでは、実際に停止したいかどうか尋ねられる場合があり、その場合は「Y」と入力してEnterを押すことができます。

これで停止し、再起動できます。それは再び「npm start」です。これで新しいタブが開くはずです。

何かを変更すると、すぐに反映されるはずです。

実際には、これらの種類のことを行う必要があることは、思っているよりも一般的です。そのため、このコースの早い段階でこの講義を含めたかったのです。

また、かなり一般的なのは、時々ブラウザでハードリロードを行うだけで済むことです。このリロードボタンをクリックするだけです。この自動リロード、つまりホットモジュール置換は、何らかの理由で常に壊れるからです。

そのため、解決策の1つは、ブラウザをハードリロードすることです。

私があなたに与えることができるもう1つの良いヒントは、常にVS Codeでターミナルを開いておくことです。ブラウザの開発ツールについても同様です。

ブラウザで右クリック→「検査」を選択して、コンソールタブを開いておくことです。React dev toolsというものもありますが、それについては少し後で話します。

これらを開いておくのが良いのは、予期しないエラーがある場合、それらがブラウザのコンソールとVS Codeの下部パネルにも表示されるからです。また、これらを開いておけば、アプリが実行されていることを常に確認できます。

エラーメッセージについて話していましたが、時々何か間違ったことをするとこれらが表示されます。Create-React-Appには、ウィンドウの上部、つまりここの上部にエラーを自動的に表示する内部機能があります。

何かここに書いてエラーを作成してみましょう。

実際にコードにエラーがあります。ブラウザ画面には表示されませんが、時々重要なエラーがブラウザ画面全体にオーバーレイとしてポップアップします。このオーバーレイがエラーメッセージを提供してくれます。

このエラーメッセージを見て、何が間違っているかを理解しようとするのが良いアイデアです。通常、エラーメッセージの最初の部分はあまり重要ではありませんが、この例では「隣接するJSX要素は囲むタグでラップする必要があります。JSXフラグメントが必要でしたか？」と言っています。

これを理解できない場合は、これをコピーして、新しいタブを開いてGoogleで検索できます。これがReactの巨大なコミュニティの力です。何百人、何千人もの人々があなたより前に同じ問題を抱え、Googleで検索したり、Stack Overflowで質問したりしているからです。そこで答えを見つけることができます。

この場合、実際にはReactで複数の要素を返すことは許可されていません。コンポーネントからh1とpの2つの要素を返そうとしており、それはReactでは許可されていません。余分な要素を削除すると、エラーが消えます。

もう1つの重要なヒントは、常にESLintと連携することです。ESLintはデフォルトで有効になっています。

例えば、これを行うと：

```javascript
const x = 'jonas';
```

保存すると、すぐにVS Codeで警告が表示されます。変数名にマウスをホバーすると、「xは宣言されていますが、その値は読み取られていません」と警告されます。

これは無数の例と状況の1つで、ESLintがあなたがすべきでないことをしようとしていることを警告してくれます。使用していない変数がある場合、それはおそらく他の場所で間違った変数を宣言したことを意味するからです。

ちなみに、これらの問題は、VS Code下部のProblemsタブにも表示されます。このタブも非常に便利です。

コードの下にこれらの黄色い線がある場合は、そこで何が起こっているかをチェックすべきです。

# 構成要素としてのコンポーネント

すでに何度か述べたように、Reactはコンポーネントがすべてですが、今度はReactコンポーネントとは何か、そしてなぜそれらがそれほど重要なのかを正式に学びましょう。

コンポーネントはReactで最も基本的な概念です。なぜなら、Reactアプリケーションは実際に完全にコンポーネントで作られているからです。

Reactアプリを見ると、コンポーネントでないもの、または少なくとも何らかのコンポーネントの内部にないものは何もありません。

したがって、私はコンポーネントがReactのユーザーインターフェースの構成要素であると言うのが好きです。

実際、基本的にReactが行うことは、コンポーネントを取ってWebページ、つまりユーザーインターフェース（略してUI）に描画することです。

それは単純に聞こえますが、実際にはReactの主な仕事です。

より技術的な用語では、Reactは各コンポーネントのビューをレンダリングし、これらすべてのビューが一緒になってユーザーインターフェースを構成します。

したがって、コンポーネントをユーザーインターフェースの一部と考えることもできます。

コンポーネントの1つの重要な特性は、各コンポーネントが独自のデータ、JavaScriptロジック、および外観を持っていることです。

基本的に、各コンポーネントはそれがどのように動作し、どのように見えるかを記述しており、これがユーザーインターフェースを構築する素晴らしい方法となっています。

ユーザーインターフェースの構築について話すと、今学んだことに基づいて、Reactでこのような複雑なUIを構築するのは理にかなっています。複数のコンポーネントを構築し、これらのコンポーネントをレゴのピースのように組み合わせることによってです。

ここでは、ビデオプレーヤー、メニュー、この質問リスト、そして表示される質問を絞り込むことができるこの部分のようなコンポーネントを識別できます。

これらは大きなコンポーネントですが、このUIでも他の多くの小さなコンポーネントを識別できます。例えば、ここのこれらのフィルターです。

このフィルターが絞り込み質問コンポーネントの内部にあることがわかります。実際、私たちが常に行うことの1つは、コンポーネントを他のコンポーネントの内部に配置すること、つまり、コンポーネントを互いにネストすることです。

コンポーネントのネストは、コンポーネントの再利用性とともに、Reactでコンポーネントを使用する重要な側面です。

質問リストに3つの類似した質問があることに注目してください。そこで、1つの質問コンポーネントを作成し、ここで3回再利用できます。

もちろん、それぞれのデータは異なりますが、propsと呼ばれるものを使用して、異なる質問コンポーネントに異なるデータを簡単に渡すことができます。これについては後で話します。

UIで重複が必要な場合は常に、新しいコンポーネントを作成し、必要な回数だけ使用します。

ご覧のように、このコース全体で学ぶ重要なスキルの1つは、このような設計をコンポーネントに分解する方法です。

それを助け、作成するコンポーネントを分析するのに役立つのは、このようなコンポーネントツリーです。

これは、ユーザーインターフェースを構成するコンポーネント間に存在する階層を示し、これらすべてのコンポーネントが互いにどのようにネストされているか、そして実際にどのように関連しているかを理解するのを非常に簡単にします。

また、絞り込み質問がフィルターの親コンポーネントであるか、逆にフィルターが絞り込み質問の子コンポーネントであるなど、コンポーネント間の関係も明確に見ることができます。

私たちは、親と子コンポーネントというこれらの用語をReactで常に使用します。それらが何を意味するかを理解することが重要です。

このようなコンポーネントツリーは、これらの種類のコンポーネント間の関係を理解するのに最適で、今のところコンポーネントについて知っておく必要があることはこれですべてです。

後で再利用性などの重要な概念について本当に深く掘り下げますが、今のところは、これらの概念の一部を実践に移しましょう。

# コンポーネントの作成と再利用

新しいコンポーネントを作成し、再利用性を初めて見ることで、アプリケーションの構築を続けましょう。

しかし、まず、GitHubからダウンロードしたファイルからこのプロジェクトのスターターファイルを取得しましょう。

starterフォルダにあるこれら3つをコピーして、プロジェクトフォルダに移動し、今のところpublicフォルダにコピーします。

ピザ画像のフォルダ、スターターデータ、そしてindex.CSSがあります。これはsourceフォルダに移動すべきでしょう。

スターターファイルを含めた後、ここにこれら2つのファイルがあることを確認してください。

それでは戻って、話していた新しいコンポーネントを作成しましょう。

Reactでは、関数を使用して新しいコンポーネントを書きます。

```javascript
function Pizza() {
  return <h2>Pizza</h2>;
}
```

これをPizzaと呼びます。なぜなら、ピザに関するデータを含むからです。今のところ、この関数にはパラメータがありません。

Reactで関数としてコンポーネントを書くときには、2つの重要なルールがあります。

まず、関数名は大文字で始まる必要があります。次に、関数は何らかのマークアップを返す必要があります。通常はJSXの形式ですが、nullを返すことも可能です。

コンポーネントからH2要素を返して、「Pizza」と書きましょう。

保存しますが、もちろんユーザーインターフェースには何も表示されません。この新しいコンポーネントをどこにも含めていないからです。ESLintも「Pizzaは定義されているが使用されていない」と警告しています。

このpizzaコンポーネントを、現在画面にレンダリングされているappコンポーネントに含めていません。

コンポーネントをこのように使用できます：

```javascript
function App() {
  return (
    <div>
      <h1>Hello React!</h1>
      <Pizza />
    </div>
  );
}
```

しかし、これはエラーを与えます。各コンポーネントは正確に1つの要素のみを返すことができ、ここにある2つの要素ではないからです。

これをdivでラップしましょう。時々VS Codeが自動的にこれらの要素を閉じるのが少し煩わしくなることがありますが、とにかく、今UIにピザが表示されます。

これで、このpizzaコンポーネントをappコンポーネント内にネストしました。ネストとは、基本的にこのコンポーネントをapp内で使用または呼び出したことを意味します。

非常に重要なことに注意してください。ネストによって、この他の関数内に関数を書くことを意味するのではありません。

決してすべきでないことは、コンポーネント宣言自体をネストすることです。これは実際にはまだ動作しますが、後で学ぶ理由で非常に悪いアイデアです。

関数宣言をネストしないでください。常にすべてのコンポーネントをトップレベルで宣言してください。

コンポーネントをネストすると言うとき、私たちが意味するのは、1つのコンポーネントを別のコンポーネントに含める、つまり呼び出すことです。

実際にこのdata.jsを削除して閉じることができます。

# JSXとは何か？

このコースでJSXの断片をすでに書いていますが、実際にJSXとは何で、なぜReactでそれほど大きな問題なのでしょうか？

最初にコンポーネントについて話したとき、コンポーネントには独自のデータ、ロジック、および外観が含まれていると話しました。

それは理にかなっていますよね？コンポーネントがユーザーインターフェースの一部である場合、そのコンポーネントがどのように見えるかを正確に記述できる必要があります。

そこでJSXが登場します。

JSXは、コンポーネントがどのように見え、データとロジックに基づいてどのように動作するかを記述するために使用する宣言的な構文です。

つまり、それはすべてコンポーネントの外観に関するものです。

実際には、これは各コンポーネントがJSXの1つのブロックを返す必要があることを意味し、ReactはそれをUIでコンポーネントをレンダリングするために使用します。

このコードを見ると、このJSXはHTMLによく似ていますよね？

しかし実際には、JSXはJavaScriptの拡張であり、HTML、CSS、JavaScriptの部分を1つのコードブロックに組み合わせることができます。

基本的に、HTMLを書いて、必要に応じてJavaScriptの断片を埋め込むことができます。例えば、JavaScript変数を参照したり、他のReactコンポーネントを参照したりして、複数のコンポーネントを組み合わせ、ネストし、再利用できます。

しかし、ReactがJavaScriptフレームワークなら、どうやってこのHTMLのようなコードを理解するのでしょうか？

JSXは単

JSXは単なるJavaScriptの拡張であることを覚えておいてください。これは、JSXをJavaScriptに変換する簡単な方法があることを意味します。

これはBabelというツールによって行われ、Create-React-Appによって自動的にアプリケーションに含まれています。

この変換の結果は、右側のこのコードのようになり、各JSX要素がReact.createElement関数呼び出しに変換されます。

これは見覚えがありませんか？これは、pure Reactの講義でappコンポーネントから返したものとまったく同じです。

そのBabelツールがなかったため、JSXを使用できなかった講義です。

とにかく、この変換は必要です。なぜなら、ブラウザはもちろんJSXを理解しないからです。ブラウザはHTMLしか理解しません。

そのため、舞台裏では、書いたすべてのJSXが多くのネストしたReact.createElement関数呼び出しに変換されます。

これらの関数呼び出しが、最終的に画面に表示されるHTML要素を作成するものです。

これが意味するのは、実際にはJSXをまったく使わずにReactを使用できるということです。

これらのcreateElement関数をJSXの代わりに手動で書くこともできますが、それはあまり楽しそうではありませんよね？

また、コードを読んで理解するのが本当に難しくなります。

そのため、実際には誰もがJSXを使用します。

さて、JSXがすべて何についてかがわかったので、JSXが宣言的な構文だと言った最初の段落に戻りましょう。

JSXが宣言的であるとはどういう意味でしょうか？

宣言的が何を意味するかを理解する前に、まず命令的が何を意味するかを確認する必要があります。

バニラJavaScriptを使用してUIを構築しようとすると、デフォルトで命令的なアプローチを使用します。

これは、要素を手動で選択し、DOMを横断し、要素にイベントハンドラーをアタッチすることを意味します。

その後、アプリで何かが起こるたびに、ボタンのクリックなど、ブラウザにそれらのDOM要素を変更する方法について段階的な指示を与え、望ましい更新されたUIに到達します。

命令的なアプローチでは、基本的にブラウザに正確にどのように物事を行うかを伝えます。

しかし、複雑なアプリでこれを行うことは完全に実行不可能です。以前に学んだすべての理由のためです。

そして、それがReactのようなフレームワークが最初に存在する理由であることを覚えておいてください。そして、Reactがユーザーインターフェースを構築するための宣言的なアプローチを使用することを選択した理由です。

宣言的なアプローチは、コンポーネントに現在あるデータに基づいて、UIが常にどのように見えるべきかを単純に記述することです。

そして、このデータがpropsとstateであることをすぐに学びます。

そのため、再び、基本的にpropsとstateに基づいてUIを記述するためにJSXを使用します。

コンポーネントに現在あるデータで、すべてDOM操作なしで起こります。

そのため、クエリセレクター、イベントリスナーの追加、クラスリスト、テキストコンテンツプロパティはどこにも見当たりません。実際、ReactはDOMから基本的に巨大な抽象化であり、私たち開発者がDOMを直接触る必要がないからです。

代わりに、UIを現在のデータの反映として考え、Reactがそのデータと自動的にUIを同期させます。

本質的に、命令的と宣言的の違いは、宣言的なアプローチでは、JSXを使用してReactに画面に何を見たいかを伝えるが、それを段階的に達成する方法は伝えないということです。

Reactは基本的にそれを自分で理解できます。

これには多くの利点があり、コース全体を通して見ていきます。

# 関心の分離

この時点で、JSXを使用していくつかのコンポーネントの外観を記述し、その中でJavaScriptも使用しました。

そして今、コンポーネントを書く経験が少しあるので、少し時間を取って、JSXがHTML、CSS、JavaScriptを1つのコードブロックに組み合わせるという事実に戻りたいと思います。

なぜReactが最初にこのアイデアを思いついたのか疑問に思うかもしれません。

なぜHTML、CSS、JavaScriptを以前のように別々の場所に保持しないのでしょうか？

これは些細な質問のように聞こえるかもしれません、あなたが全く関連性がないと思うものですが、実際にはReactがコンポーネントを中心に完全に設計された理由を理解するために深く関連しています。

このトピックを最初から理解しましょう。

インタラクティブなシングルページアプリケーションの台頭から。

シングルページアプリの前は、常にHTMLに1つのファイル、JavaScriptに1つ、CSSに1つありました。

基本的に、ファイルごとに1つの技術。

それが私たちの伝統的な関心の分離でした。

私と同じように、これがあなたが最初にWeb開発を学んだ方法だと確信しています。

しかし、ページがますますインタラクティブになり、シングルページアプリケーションになると、JavaScriptがユーザーインターフェースとコンテンツ全般を決定し始めました。

言い換えれば、JavaScriptがHTMLをますます担当するようになりました。

この本当に小さなコード例で見ることができます。ここで、これらのHTML要素のコンテンツとプレゼンテーションは、JavaScriptコードによって完全に決定されています。

実際、それらは密接に結合されています。

HTMLはここのJavaScriptなしでは意味をなしません。

このコードの詳細は本当に重要ではありません。

このコードを読めない場合、それは全く問題ありません。

私のポイントは、JavaScriptがとにかくHTMLを担当している場合、ロジックとUIが非常に密接に結合されている場合、なぜそれらを異なるファイルや異なるコードブロックで分離しておく必要があるのかということです。

その質問への答えが、ReactコンポーネントとJSXを与えてくれました。

ロジックとUIが現代のWebアプリケーションで非常に結合されているという事実は、Reactコンポーネントがデータ、ロジック、UIの1つの部分の外観を含む理由です。

実際、それがReactがすべてコンポーネントに関する基本的な理由です。

同じことが、他のほとんどの現代のフロントエンドフレームワークにも実際に当てはまります。

コードに戻ると、このReactの例では、JavaScriptとHTMLマークアップがこの1つのコンポーネントで非常に幸せに一緒に住んでいることがわかります。

このコンポーネントにはJavaScriptロジックがあり、JSXがあり、そのJSX内に別のJavaScriptブロックがあり、それにはさらにJSX内部があります。

すべてが混在していますが、それでもすべて本当にうまく機能します。

コンテンツとロジックが密接に結合されているため、ここで共存することは理にかなっています。

共存とは、一緒に変更されるものは可能な限り近くに配置されるべきであることを意味します。

Reactアプリの場合、1つの技術ファイルの代わりに、1つのコンポーネントファイルがあることを意味します。

データロジックと外観がすべて混在した1つのコンポーネント。

ReactとJSXが長い間前に出てきたとき、多くの人々がJSXの見た目を嫌っていました。

関心の分離を窓から投げ捨てていることを嫌っていました。

しかし、実際に、私たちは本当にそうしているのでしょうか？

Reactには本当に関心の分離がないのでしょうか？

Reactには関心の分離がないと言う人々は、すべて間違っていると思います。

Reactには実際に関心の分離があるからです。

従来のようにファイルごとに1つの関心ではなく、コンポーネントごとに1つの関心です。

各コンポーネントは実際に、UIの1つの部分にのみ関心があります。

これらの各コンポーネント内で、もちろん、HTML、CSS、JavaScriptの3つの関心がすべて混在しています。私たちが議論してきたように。

従来の関心の分離と比較して、これは多くの人が最初に本当に慣れていなかった完全に新しいパラダイムです。

しかし、今、何年も後、私たちは皆これに慣れ、それは素晴らしく機能します。

特定のコンポーネントに関するすべての情報を1つの場所に持つことは、本当に素晴らしい方法で機能します。

これは長い講義でした、私が期待していたよりも長く、この結論に到達するためだけに、Reactには実際に関心の分離があります。

ただ、異なる関心の分離です。

# Reactアプリケーションのスタイリング

この時点で、Reactコンポーネントにはcssスタイルも含めることができることを知っています。

そこで、Reactアプリケーションにcssを適用するいくつかの簡単な方法について学びましょう。

Reactでは、コンポーネントをスタイリングする多くの異なる方法があり、Reactはそれをどのように行うかについて実際に気にしません。

スタイリングについて意見を持っていません。

その理由は、最初に学んだように、Reactは実際にはフレームワークというよりもライブラリだからです。

そのため、コンポーネントをスタイリングする方法、最終的にはアプリケーションをスタイリングする方法について、好ましい方法がありません。したがって、多くの異なるオプションから選択できます。

例えば、インラインスタイリング、外部CSSまたはSASSファイルを使用できます。

# Props、不変性、一方向データフロー

propsが何であり、実際にどのように使用するかをすでに知っているので、それらを素早く復習し、propsについてさらに重要なことを学びましょう。

学んだように、Reactでpropsをuseしてデータをparentコンポーネントからchildコンポーネントに渡します。

本質的に、コンポーネントツリーの下に情報を渡すために。

これは、本質的にparentとchildコンポーネント間の通信にpropsを使用することを意味します。

したがって、propsはコンポーネントを構成し、カスタマイズするための重要なReactツールです。

propsを、parentコンポーネントがchildコンポーネントがどのように見え、どのように動作するかを制御するために使用できる設定として想像できます。

その点で、propsは通常のJavaScript関数に渡される引数のようなものです。

また、JavaScript関数に何でも渡すことができますよね？

propsについても同じことが実際に当てはまります。

任意のタイプの値をpropとして渡すことができます。

単一の値、配列オブジェクト、関数、さらには他のReactコンポーネントも渡すことができます。これは後で探求する本当に強力なテクニックです。

これらがReactのpropsの基本ですが、今度は少し深く掘り下げてみましょう。

しかし、その前に、一歩下がる必要があります。

コースのこの時点で、コンポーネントの外観とロジックについてすでに学びました。

JSXとコンポーネント内のJavaScriptロジックの両方を書くことによって。

また、コースの最初から、Reactが現在のデータに基づいてコンポーネントをレンダリングし、UIが常にそのデータと同期を保つと言ってきました。

しかし、今度はそのデータが実際に何であるかについてもう少し具体的になる時です。

Reactがコンポーネントをレンダリングするために使用するこのデータは、propsとstateで構成されています。

実際には他のタイプのデータもありますが、今重要なのはpropsとstateです。

stateは基本的に内部コンポーネントデータで、コンポーネントのロジック、つまりコンポーネント自体によって更新できます。

一方、propsは親コンポーネントから来るデータ、つまり基本的に外部からのデータです。

親コンポーネントがそのデータを所有しているため、子コンポーネントによって変更することはできません。

代わりに、propsは親コンポーネント自体によってのみ更新できます。

これにより、Reactが与える数少ない厳格なルールの1つになります。propsは不変です。

変更できません。読み取り専用です。

propsを変更する必要があると感じる場合、実際に必要なのはstateです。

stateは時間の経過とともに変化するデータのためのものだからです。すぐに学びます。

しかし、なぜそうなのでしょうか？

なぜpropsはReactで不変なのでしょうか？

まず、propsは単なるオブジェクトです。

したがって、コンポーネント内でpropsオブジェクトを変更すると、親コンポーネントにも影響を与えます。

それがJavaScriptでオブジェクトが動作する方法だからです。

オブジェクトをコピーしてコピーを変更すると、元のオブジェクトも変更されます。

関数の外部にあるオブジェクトを変更すると、その関数は副作用を作成したことになります。

一般的に、副作用は現在の関数の外部にあるデータを変更するときに発生します。

しかし、Reactは純粋な関数がすべてです。

少なくともコンポーネントのデータに関しては、副作用のない関数です。

コンポーネントは、propsとstateに関して純粋でなければなりません。

これにより、Reactはアプリケーションを最適化でき、外部データを操作するときに現れる可能性のある奇妙なバグを回避できます。

実際、この不変性のアイデアをReact開発全般に拡張できます。

コンポーネントは、関数スコープの外部に書いたデータを決して変更すべきではありません。

最後に、Reactがいわゆる一方向データフローを使用することを理解することが重要です。

これはpropsと何の関係があるのでしょうか？

簡単に言うと、一方向データフローは、Reactアプリケーションでは、データは親から子コンポーネントにのみ渡すことができることを意味します。これはpropsを使用して行われます。

言い換えれば、データは親から子に流れることができますが、決して逆方向には流れません。

したがって、コンポーネントツリーの上から下への一方向データフローがあります。

これはあなたには明らかに聞こえるかもしれませんが、Angularなどの他のフレームワークは実際に双方向データフローを採用しています。

これらのフレームワークのいずれかをすでに知っている場合、これはあなたにとってかなりの変化かもしれません。

しかし、実際にReactがこのような一方向データフローを使用する理由または複数の理由があります。

最初は、アプリケーションをはるかに予測可能で、開発者にとって理解しやすくします。

データが一方向にのみ流れる場合、データがどこから来ているかを理解するのがはるかに簡単だからです。

同様に、アプリケーションをデバッグするのがはるかに簡単になります。

# Propsの分割代入

propsを使用する際の生活を少し楽にするテクニックを学びましょう。

現在、pizzaコンポーネントでは、props.pizzaObj.nameのように、非常に長い方法でpropsにアクセスしています。

これは少し面倒で、読みにくくなる可能性があります。

そこで、JavaScriptの分割代入を使用して、これを改善できます。

```javascript
function Pizza(props) {
  const { name, ingredients, price, photoName, soldOut } = props.pizzaObj;
  
  if (soldOut) {
    return null;
  }

  return (
    <li className="pizza">
      <img src={photoName} alt={name} />
      <div>
        <h3>{name}</h3>
        <p>{ingredients}</p>
        <span>{price}</span>
      </div>
    </li>
  );
}
```

これで、props.pizzaObj.nameの代わりに、単純にnameを使用できます。

さらに良いのは、関数のパラメータレベルで分割代入を行うことです。

```javascript
function Pizza({ pizzaObj }) {
  const { name, ingredients, price, photoName, soldOut } = pizzaObj;
  
  if (soldOut) {
    return null;
  }

  return (
    <li className="pizza">
      <img src={photoName} alt={name} />
      <div>
        <h3>{name}</h3>
        <p>{ingredients}</p>
        <span>{price}</span>
      </div>
    </li>
  );
}
```

これにより、コードがより読みやすく、簡潔になります。

同じことをorderコンポーネントでも行いましょう。

```javascript
function Order({ closeHour }) {
  return (
    <div className="order">
      <p>We're open until {closeHour}:00. Come visit us or order online.</p>
      <button className="btn">Order</button>
    </div>
  );
}
```

分割代入は、Reactでpropsを扱う際の非常に一般的で有用なテクニックです。

# React Fragments

時々、JSXで余分なdivやその他の要素を作成したくない場合があります。

例えば、コンポーネントから複数の要素を返したいが、それらを不要なdivでラップしたくない場合です。

そのような場合に、React Fragmentsが役立ちます。

React Fragmentは、追加のDOMノードを作成せずに、子要素のリストをグループ化できます。

```javascript
function Header() {
  return (
    <React.Fragment>
      <h1 style={style}>Fast React Pizza Co.</h1>
      <p>Authentic Italian cuisine</p>
    </React.Fragment>
  );
}
```

または、短縮構文を使用できます。

```javascript
function Header() {
  return (
    <>
      <h1 style={style}>Fast React Pizza Co.</h1>
      <p>Authentic Italian cuisine</p>
    </>
  );
}
```

この短縮構文（<>と</>）は、React.Fragmentと同じ機能を提供しますが、より簡潔です。

ただし、keyプロパティが必要な場合（リストをレンダリングする際など）は、完全な構文を使用する必要があります。

```javascript
{items.map(item => (
  <React.Fragment key={item.id}>
    <h3>{item.title}</h3>
    <p>{item.description}</p>
  </React.Fragment>
))}
```

React Fragmentsは、セマンティックHTMLを維持し、不要なDOM要素を避けるのに役立ちます。

# 動的スタイリング

最後に、条件に基づいてスタイルを動的に適用する方法を学びましょう。

pizzaコンポーネントで、売り切れのピザに特別なスタイリングを適用したいとします。

まず、売り切れのピザを非表示にするのではなく、表示するように変更しましょう。

```javascript
function Pizza({ pizzaObj }) {
  const { name, ingredients, price, photoName, soldOut } = pizzaObj;

  return (
    <li className="pizza">
      <img src={photoName} alt={name} />
      <div>
        <h3>{name}</h3>
        <p>{ingredients}</p>
        <span>{soldOut ? "SOLD OUT" : `€${price}`}</span>
      </div>
    </li>
  );
}
```

次に、売り切れのピザに特別なクラスを適用しましょう。

```javascript
function Pizza({ pizzaObj }) {
  const { name, ingredients, price, photoName, soldOut } = pizzaObj;

  return (
    <li className={soldOut ? "pizza sold-out" : "pizza"}>
      <img src={photoName} alt={name} />
      <div>
        <h3>{name}</h3>
        <p>{ingredients}</p>
        <span>{soldOut ? "SOLD OUT" : `€${price}`}</span>
      </div>
    </li>
  );
}
```

さらに良い方法は、テンプレートリテラルを使用することです。

```javascript
function Pizza({ pizzaObj }) {
  const { name, ingredients, price, photoName, soldOut } = pizzaObj;

  return (
    <li className={`pizza ${soldOut ? "sold-out" : ""}`}>
      <img src={photoName} alt={name} />
      <div>
        <h3>{name}</h3>
        <p>{ingredients}</p>
        <span>{soldOut ? "SOLD OUT" : `€${price}`}</span>
      </div>
    </li>
  );
}
```

これにより、売り切れのピザには"pizza sold-out"クラスが適用され、通常のピザには"pizza"クラスのみが適用されます。

CSSでは、sold-outクラスに特別なスタイル（例：グレーアウト、透明度の変更など）を定義できます。

```css
.sold-out {
  color: #888;
  opacity: 0.6;
}

.sold-out img {
  filter: grayscale(100%);
}
```

これで、動的スタイリングの基本を理解しました。条件に基づいてクラス名を変更し、CSSでそれらのクラスに異なるスタイルを適用することで、インタラクティブで視覚的に魅力的なUIを作成できます。
