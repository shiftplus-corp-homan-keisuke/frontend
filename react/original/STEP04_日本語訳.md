# UI をコンポーネントに分割する方法

React の考え方に関するセクションに戻ってきました。このセクションでは、状態、データの流れ、コンポーネントについて扱います。状態管理についてはすでに詳しく説明したので、次はコンポーネントについてもっと話す時です。

コンポーネントに関しては、UI をコンポーネントにどのように分割するか、そしていつ新しいコンポーネントを作成すべきか、という重要な質問を自分自身に問いかける必要があります。このビデオでは、これらの質問に答えようと思います。

これらの質問に答えるための 1 つの方法は、コンポーネントのサイズに注目することです。すべてのコンポーネントをそのサイズに基づいて分類できる、つまり、すべてのコンポーネントをこのコンポーネントサイズの軸上に配置できるということです。一方には非常に小さなコンポーネントがあり、もう一方の極端には巨大なコンポーネントがあります。多くの場合、これらの極端なものは理想的ではありません。

このシンプルなカードを構築したいと想像してみてください。1 つの方法は、カード全体に対して 1 つの巨大なコンポーネントを作成することです。しかし、それは一連の問題を引き起こします。まず、このコンポーネントにはあまりにも多くのことが起こっており、責任が多すぎます。

コンポーネントは JavaScript 関数と非常によく似ています。関数があまりにも多くの異なることを行う場合、それを複数の関数に分割すべきです。そして、同じことが React コンポーネントにも当てはまります。

コンポーネントが大きすぎるということが明らかになるもう一つの方法は、正しく機能するためにあまりにも多くのプロップを受け取る必要がある場合です。例えば、特定のコンポーネントを適切に設定するために 10 個または 15 個のプロップが必要な場合、そのコンポーネントはおそらく大きすぎ、分割すべきです。

一般的に、これら 2 つの問題は、コンポーネントの再利用を非常に困難にします。これは、そもそもコンポーネントの大きな利点の 1 つです。また、巨大なコンポーネントは一般的に複雑で絡み合ったコードを多く含んでおり、最終的にコンポーネント全体を理解しにくく、使いにくくしています。

では、これは反対に、このように多くの小さなコンポーネントを作成すべきだという意味でしょうか？まあ、ほとんどの場合、それもひどい考えでしょう。もしこの方法で UI やアプリケーション全体を構築すると、何百、いや何千ものミニコンポーネントで終わることになります。

これはもちろん、ナビゲートしにくく、理解しにくい、非常に混乱したコードベースを作成し、抽象化されすぎることになります。そして、抽象化という用語に慣れていない方のために説明すると、プログラミングでは基本的に、あるものの実装の詳細を隠すために新しいものを作成することを意味します。

例えば、ボタンコンポーネントを作成する場合、そのコンポーネントのユーザーは、ボタンが実際にどのように機能するかを知らないかもしれません。なぜなら、実装の詳細は、この抽象化、つまりこのコンポーネントの背後に隠されているからです。つまり、ある意味で、私たちが作成する新しいコンポーネントはすべて抽象化なのです。

さて、スペクトルの両端、つまり非常に小さなコンポーネントと巨大なコンポーネントの両方にこれらの問題がある場合、どうすればよいのでしょうか？ほとんどの場合、目標は、具体的すぎず、広すぎず、言い換えれば、小さすぎず、大きすぎない、適切なバランスを取るコンポーネントを作成することです。

ここで特定した問題、例えばコンポーネントの責任が多すぎたり、再利用が困難だったりすることは、UI をコンポーネントに実際にどのように分割すべきかを理解するのに役立ちます。

先ほどと同じ例を使って説明すると、最初は 1 つの巨大なコンポーネントだけで、次に多くの小さなコンポーネントがありましたが、UI を分割するこれらの両方の方法は、私たちが話したすべての理由から理想とはかけ離れています。

したがって、私たちが望むのは、このようなものです。ここでは、コンテンツが異なるコンポーネントに、より論理的に分離されており、これらのコンポーネントの中には、ハートボタンや SUPERHOST ラベルのように、再利用可能なものもあるでしょう。また、これらの各コンポーネントには、価格や評価の表示など、明確に定義された責任があり、過度に複雑でもありません。

さて、これから、ユーザーインターフェースをコンポーネントに分割するために使用できるいくつかの基準を導き出すことができます。まず、特定の UI を実装するためにどのコンポーネントが必要かを決定する際には、これらのコンポーネントがコンテンツ、あるいはページのレイアウトの論理的な分離を作成することが重要です。

また、これらのコンポーネントの一部を再利用可能にし、各コンポーネントが単一の明確に定義された責任を持つように努めるべきです。最後に、さらに主観的な基準が 1 つあります。それはあなたの個人的なコーディングスタイルです。

一部の人々はより小さなコンポーネントでより良く働き、一部の人々はより大きなコンポーネントを好むため、可能な限り生産性を維持できるように、自分にとって最適な方法でコンポーネントを作成する必要があります。さて、それでは、これらすべての異なる基準についてもう少し深く掘り下げてみましょう。

このスライドで私がしたいことは、より大きなコンポーネントから新しいコンポーネントを作成するのに役立つ、一種のフレームワークを提供することです。つまり、新しいコンポーネントを作成していて、そのコンポーネントに何を含めるべきか迷った場合、比較的に大きなコンポーネントから始めて、ただし巨大なコンポーネントではなく、必要に応じてその大きなコンポーネントを小さなコンポーネントに分割するという考え方です。

しかし、当然、あなたは今、「いつ大きなコンポーネントを複数の小さなものに分割する必要があるのか？」と尋ねるでしょう。さて、そこで再び 4 つの基準が登場します。コンテンツの論理的な分離、再利用性、コンポーネントの責任と複雑さ、そしてあなたの個人的なコーディングスタイルです。

もちろん、ボタンのような小さくて再利用可能なコンポーネントが必要だとすでにわかっている場合は、これらすべてをスキップして単にコンポーネントを作成するだけで済みます。しかし、そうでなければ、最初は大きく始めても構いませんし、最初から再利用性や複雑さに焦点を当てる必要はありません。

しかし、いずれかの時点で、これらのトピックについて心配する必要があるため、論理的な分離から始めて、1 つずつ分析していきましょう。

もし、大きなコンポーネントを書いた後、そのコンポーネントにコードの一部、あるいはレイアウトの一部で、実際には一緒にするべきではないと感じる部分が含まれていると感じたら、それはおそらく新しいコンポーネントを作成する良いアイデアだということです。

再利用性についてですが、もしあなたの大きなコンポーネントの一部を再利用することが可能で、実際にその部分を再利用したい、あるいは必要とするのであれば、そのコードを取り出して新しいコンポーネントに抽出するべきです。

あなたのコンポーネントの一部を新しいコンポーネントに抽出するべきだというもう一つの兆候は、あなたのコンポーネントがあまりにも多くの異なることを行っているか、あまりにも多くのプロップに依存している場合です。

もしあなたの大きなコンポーネントが状態やエフェクトのピースを多すぎたり、コードが複雑すぎたり混乱しすぎたりしている場合、それはもう一度、新しい、より小さなコンポーネントを作成する時期かもしれません。

そして最後に、前のスライドで述べたように、コンポーネントを扱う際に生産的だと感じることが重要です。もしあなたがより小さな関数やコンポーネントを好むなら、大きなコンポーネントを小さなものに分割してください。しかし、反対に、大きなコンポーネントを好むなら、それも全く問題ありません。

最終的にはすべてあなた次第です。なぜなら、これらはすべて、時間が経つにつれて直感的になるガイドラインとベストプラクティスに過ぎず、その頃にはコンポーネントを構築することはあなたの第二の天性になっているでしょう。しかし、今始めるときは、このようなガイドラインが役立つのは素晴らしいことです。

そして、ガイドラインと言えば、他にもいくつか一般的なガイドラインがあります。まず、新しいコンポーネントを作成することは、新しい抽象化を作成することに注意する必要があります。そして、この講義で以前に抽象化について少し話しましたよね？

抽象化にはコストがかかります。なぜなら、より多くの抽象化を持つことは、異なるコンポーネントについて考えたり、コンポーネント間を行ったり来たりするために、より多くの精神的なエネルギーを必要とするからです。したがって、可能であれば、あまりに早く新しいコンポーネントを作成しないように努めてください。

次に、コンポーネントにそれが何をするのか、何をどのように表示するのかにちなんで名前を付けることが重要です。そして、長いコンポーネント名を使用することを恐れないでください。React 開発では完全に普通のことです。

さらに重要なのは、決して、決して、別のコンポーネントの内部で新しいコンポーネントを宣言しないことです。その理由については、次のセクションで学びます。代わりにできることは、関連するコンポーネントがある場合、これらの関連するコンポーネントを同じファイル内にまとめて配置することです。

最後に、そしてコンポーネントサイズの最初のトピックに戻りますが、アプリケーションに非常に小さなコンポーネントや巨大なコンポーネントを含む、さまざまなサイズのコンポーネントがあることは完全に正常です。

ですから、最初に非常に小さなコンポーネントにはいくつかの問題があると述べましたが、もちろん、どんなアプリケーションでも、これらのような小さなコンポーネントは常に必要です。なぜなら、それらは高度に再利用可能であり、非常に低い複雑性を持っているからです。これは、私たちが必要とするものとまったく同じ場合もあります。

ほとんどのアプリには、再利用を意図していない巨大なコンポーネントもいくつかあります。例えば、アプリ全体またはページのレイアウトを含む巨大なページコンポーネントがあるかもしれません。これは非常に複雑なコンポーネントであり、再利用を意図していない可能性が十分にあります。

このような状況では、再利用性やこのコンポーネントを分割する必要があることについて心配する必要はありません。そして、再利用性について言えば、これからわかるように、一般的なルールとして、再利用性の範囲はサイズの範囲とかなり似ていると言えます。

つまり、一般的に言えば、コンポーネントが小さいほど、再利用可能になります。そしてもちろん、コンポーネントが大きくなるにつれて、再利用性は低下します。しかし、繰り返しになりますが、一部のコンポーネントにとっては全く問題ありません。つまり、すべてのコンポーネントが再利用可能であるとは限りません。

しかし、とにかく、最後に、さまざまな程度のサイズ、再利用性、責任、複雑性を持つ、これらすべての中規模のコンポーネントもあります。つまり、最終的には、私たちのアプリケーションにはスペクトル全体にわたって多くの異なるコンポーネントが存在し、それは完全に正常で自然なことです。

さあ、コーディングに戻り、学んだばかりのすべての概念を使って、巨大なコンポーネントを多くの小さなものに分割しましょう。

# コンポーネントのカテゴリ

いくつかの異なるコンポーネントを作成したところで、ほとんどの React コードベースで自然に発生する異なるコンポーネントカテゴリについて簡単に説明しましょう。

コンポーネントのほとんどは、自然に 3 つのカテゴリのいずれかに分類されます。ステートレスまたはプレゼンテーションコンポーネント、ステートフルコンポーネント、構造コンポーネントです。そして、自然にと言うのは、コンポーネントをこれらのカテゴリのいずれかに強制すべきではないからです。

ステートレスまたはプレゼンテーションコンポーネントから始めます。名前が示すように、これらには状態がありません。通常、これらはいくつかのプロップを受け取り、そのデータまたは他のコンテンツを単に提示するコンポーネントであり、そのためプレゼンテーションという名前が付いています。多くの場合、これらは現在のアプリのロゴ、numResults、ムービーコンポーネントなどのかなり小さなコンポーネントです。

次に、ステートフルコンポーネントは、単に状態を持つコンポーネントです。これらのコンポーネントが状態を持っているからといって、高度に再利用できないわけではありません。たとえば、私たちが構築した検索コンポーネントには状態があり、この入力はアプリ全体で何度でも再利用できます。

最後に、構造コンポーネントは、アプリケーションのページ、レイアウト、または画面と考えることができます。これらは、多くの場合、多くの小さなコンポーネントを組み合わせて構成した結果です。コンポジションについては、このセクションの後半で詳しく説明します。

したがって、これらの構造コンポーネントは、大きく、再利用できないコンポーネントである場合がありますが、そうである必要はありません。構造コンポーネントは、非常に小さい場合もあります。重要なのは、ページやレイアウトなど、アプリケーションに何らかの構造を提供する責任があることです。

# コンポーネント API としての Props

現在構築中のような再利用可能なコンポーネントを構築する際には、そのコンポーネントに必要なプロップについて慎重に検討する必要があります。そこで、プロップについてどのように考えるべきかを簡単に見てみましょう。

まず、コンポーネントの作業を始めるときは、コンポーネントは常に誰かによって作成され、常に誰かによって消費されるという考え方を持つべきです。自分で作業している場合、コンポーネントの作成者と消費者はもちろん同じ人物です。

しかし、チームで作業している場合、それらは異なる開発者である可能性が十分にあります。しかし、いずれにせよ、たとえ自分自身だけで作業している場合でも、コンポーネントの作成者と消費者がいるという考え方で作業するのは常に良いことです。
