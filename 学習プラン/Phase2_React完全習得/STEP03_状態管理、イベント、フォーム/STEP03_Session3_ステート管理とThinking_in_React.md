## react の流儀 とは

React アプリケーションを構築するには、単に React API の使い方を学ぶだけでは不十分です。**React の考え方（react の流儀）**という、全く新しいマインドセットを身につける必要があります。

### React マインドセットの重要性

**従来の JavaScript との違い**：

- バニラ JavaScript でのアプリケーション構築とは根本的に異なるアプローチ
- **要素の操作**から**状態の遷移**への思考の転換が必要
- コンポーネント、state、props、データフロー、effects などの React ツールの適切な使い方の習得

**React マスタリーの 2 つの柱**：

1. **React API の実践的スキル**: useState などの関数の使用方法
2. **react の流儀**: いつ、どのように React ツールを使うかの判断力

### react の流儀 のプロセス

React アプリケーション構築は、構造化されたプロセスとして捉えることができます：

#### 1. UI のコンポーネント分割

**目標**: 望ましい UI をコンポーネントに分解し、コンポーネント間の関係を確立

**考慮事項**：

- **再利用性**: コンポーネントがどの程度再利用可能か
- **構成性**: コンポーネントをどのように組み合わせて大きな機能を作るか
- **責任の分離**: 各コンポーネントが明確で単一の責任を持つか

#### 2. 静的バージョンの構築

**目標**: 状態やインタラクティブ性なしで、アプリケーションの静的版を構築

**利点**：

- **コーディングの前倒し**: 状態管理を考える前に、大部分のコードを完成
- **構造の確認**: UI 構造とコンポーネント階層の検証
- **デザインの実装**: ビジュアルデザインをコードに落とし込み

#### 3. 状態について考える

**決定事項**：

- **いつ状態が必要か**: どのタイミングで状態を作成するべきか
- **どのような種類の状態か**: ローカル、グローバル、派生状態など
- **どこに配置するか**: どのコンポーネントが状態を所有すべきか

#### 4. データフローの確立

**実装内容**：

- **一方向データフロー**: 親から子への適切なデータの流れ
- **親子間通信**: 子コンポーネントから親への情報伝達
- **グローバル状態のアクセス**: アプリケーション全体での状態共有

### react の流儀 で解決できる問題

このマインドセットを身につけることで、以下のような設計上の問題に答えられるようになります：

**コンポーネント設計**：

- UI デザインをどのようにコンポーネントに分割するか？
- コンポーネントを真に再利用可能にするにはどうするか？
- 再利用可能なコンポーネントから UI を組み立てるにはどうするか？

**状態管理**：

- 必要なインタラクティブ性のために、どの状態が必要か？
- 各状態をどこに配置するか（どのコンポーネントが所有するか）？
- どのような種類の状態を使用するか？
- データをアプリケーション全体でどのように流すか？

## ステート管理の基本原則

ステートは React における最も重要な概念です。したがって、ステート管理は「react の流儀」の最も重要な側面となります。ステート管理の基本原則について詳しく学習しましょう。

### ステートの役割と複雑性

**アプリケーションでのステートの例**：
一般的な Web アプリケーション（例：Udemy）では、多数のステート変数が同時に存在します：

- ユーザー認証状態
- ショッピングカートの内容
- 検索クエリ
- フィルター設定
- 現在のページ情報
- ローディング状態
- エラー状態

このように多くのステートが存在すると、どこに何を配置すべきかが複雑になります。

### ステート管理の定義

**ステート管理とは**：

- **作成時期の決定**: いつ新しいステートを作成する必要があるか
- **種類の選択**: どのような種類のステートが必要か
- **配置場所の決定**: コードベース内のどこに各ステートを配置するか
- **データフローの設計**: アプリケーション全体でデータをどのように流すか

**比喩的表現**: ステート管理は、**各ステートにコードベース内での「家」を与える**こと

### ローカルステート vs グローバルステート

React におけるステートは、大きく 2 つのカテゴリに分類されます：

#### ローカルステート（Local State）

**特徴**：

- **限定的なアクセス**: 1 つのコンポーネント、または少数の関連コンポーネントでのみ必要
- **作成方法**: `useState` フックを使用して特定のコンポーネント内で作成
- **アクセス範囲**: そのコンポーネントとその子コンポーネント（props を通じて）

**使用例**：

```jsx
function SearchBar() {
  const [searchText, setSearchText] = useState(""); // ローカルステート

  // この検索テキストは、おそらくSearchBarコンポーネントでのみ必要
  return (
    <input value={searchText} onChange={(e) => setSearchText(e.target.value)} />
  );
}
```

#### グローバルステート（Global State）

**特徴**：

- **広範囲のアクセス**: アプリケーション内の多数のコンポーネントでアクセスが必要
- **作成方法**: Context API や外部ライブラリ（Redux 等）を使用
- **共有性**: すべてのコンポーネントからアクセス可能

**使用例**：

- ショッピングカート（複数のコンポーネントで表示・更新が必要）
- ユーザー認証状態（ヘッダー、サイドバー、保護されたページなどで必要）
- テーマ設定（アプリケーション全体の外観に影響）

### ステート管理のガイドライン

**基本原則**: 常に**ローカルステートから始める**

1. **段階的なアプローチ**: 最初はローカルステートで実装
2. **必要性の検証**: 本当にグローバルステートが必要になった時点で移行
3. **過度な複雑化の回避**: 不必要なグローバルステートは避ける

### ステート配置の決定フローチャート

ステートをいつ作成し、どこに配置するかを決定するためのフローチャート：

#### 1. データの変化性チェック

**質問**: このデータは時間の経過とともに変化するか？

- **No**: 通常の変数（const）で十分
- **Yes**: 次のステップへ

#### 2. 派生可能性チェック

**質問**: 既存のステートや props から計算できるか？

- **Yes**: **派生ステート**として実装（後のセクションで詳細解説）
- **No**: 次のステップへ

#### 3. 再レンダリング必要性チェック

**質問**: ステート更新時にコンポーネントの再レンダリングが必要か？

- **No**: **Ref**を使用（特殊なケース、後で学習）
- **Yes**: 次のステップへ

#### 4. useState での作成

**結論**: `useState` フックを使用してローカルステートを作成

#### 5. 使用範囲の確認

**現在のコンポーネントでのみ使用**: そのまま配置

**子コンポーネントでも必要**: props として渡す

**兄弟コンポーネントや親コンポーネントでも必要**: **ステートのリフトアップ**

### 実践的なアプローチ

この決定プロセスは、最初は複雑に感じるかもしれませんが、経験を積むことで直感的に判断できるようになります：

- **いつステートを作成するか**
- **いつ派生ステートを使用するか**
- **いつステートをリフトアップするか**

これらの判断が自然にできるようになることが、React マスタリーの重要な指標です。

このフローチャートは学習初期の指針として活用し、徐々に自然な判断力を身につけていきましょう。

## ステートのリフトアップの実装

前回のセッションで発見したコンポーネント間でのデータ共有問題を、「ステートのリフトアップ」という重要な技術を使用して解決します。実際のコードでこの概念を実装していきましょう。

### 現在の状況の再確認

**Far Away アプリケーションの状況**：

- **フォーム機能**: 制御されたコンポーネントで動作中
  - `description` と `quantity` のステート管理
  - フォーム送信時の適切なデータ処理
  - バリデーションとリセット機能

**現在のデータフロー**：

```
Form コンポーネント → console.log(newItem)
```

**目標のデータフロー**：

```
Form コンポーネント → アイテム配列 → PackingList コンポーネント
```

### ステート配置の決定

ステート管理フローチャートを適用して、適切な配置を決定します：

**判断プロセス**：

1. **変化性**: アイテムデータは時間とともに変化する ✓
2. **派生可能性**: 既存の state から計算不可 ✓
3. **再レンダリング**: UI 更新が必要 ✓
4. **使用範囲**:
   - Form（更新用）+ PackingList（表示用）= 兄弟コンポーネント

**結論**: **共通の親コンポーネント（App）**にステートをリフトアップ

### App コンポーネントでのステート作成

```jsx
function App() {
  const [items, setItems] = useState([]);

  function handleAddItems(item) {
    setItems((items) => [...items, item]);
  }

  return (
    <div className="app">
      <Logo />
      <Form onAddItems={handleAddItems} />
      <PackingList items={items} />
      <Stats />
    </div>
  );
}
```

**重要なポイント**：

- **ステートの所有**: App コンポーネントが `items` ステートを所有
- **更新ロジック**: `handleAddItems` 関数も App 内で定義
- **イミュータブル更新**: スプレッド演算子で新しい配列を作成

### Form コンポーネントの修正

```jsx
function Form({ onAddItems }) {
  const [description, setDescription] = useState("");
  const [quantity, setQuantity] = useState(1);

  function handleSubmit(e) {
    e.preventDefault();

    if (!description) return;

    const newItem = {
      description,
      quantity,
      packed: false,
      id: Date.now(),
    };

    onAddItems(newItem); // 親の関数を呼び出し

    setDescription("");
    setQuantity(1);
  }

  // JSX は同じ...
}
```

**変更点の説明**：

- **props の受け取り**: `{ onAddItems }` で親からの関数を受け取り
- **ステートの削除**: `items` ステートは削除（親に移動）
- **関数呼び出し**: `onAddItems(newItem)` で親の状態を更新

### PackingList コンポーネントの修正

```jsx
function PackingList({ items }) {
  return (
    <div>
      <ul className="list">
        {items.map((item) => (
          <Item item={item} key={item.id} />
        ))}
      </ul>
    </div>
  );
}
```

**変更点**：

- **props の受け取り**: `{ items }` で親からのデータを受け取り
- **初期データの削除**: `initialItems` の使用を停止
- **動的レンダリング**: 実際のアプリケーションステートを使用

### データフローの確認

**完成したデータフロー**：

1. **Form でのアイテム作成**:

   ```
   User Input → handleSubmit → newItem object → onAddItems(newItem)
   ```

2. **App でのステート更新**:

   ```
   onAddItems → handleAddItems → setItems → items state 更新
   ```

3. **PackingList での表示**:
   ```
   items state → props → PackingList → 個別 Item コンポーネント
   ```

### 動作確認

実際にアプリケーションをテストして、以下を確認します：

**期待される動作**：

1. フォームに「10 個のシャツ」を入力
2. 送信ボタンクリックまたは Enter キー
3. PackingList に新しいアイテムが表示
4. フォームが自動的にリセット
5. React Dev Tools で `items` ステートの更新を確認

**動作検証例**：

```jsx
// 入力例 1
{ description: "Shirts", quantity: 10, packed: false, id: 1703123456789 }

// 入力例 2
{ description: "Boarding passes", quantity: 2, packed: false, id: 1703123456790 }
```

### ステートのリフトアップの意義

**解決された問題**：

- **データ共有**: 兄弟コンポーネント間でのデータアクセス
- **状態の一元化**: アプリケーション状態の単一の真実のソース
- **関心の分離**: 各コンポーネントが適切な責任を持つ

**設計上の利点**：

- **Form**: データ作成に集中
- **PackingList**: データ表示に集中
- **App**: データ管理と調整に集中

この実装により、スケーラブルで保守しやすい React アプリケーションの基盤が完成しました。次のセッションでは、この基盤の上にアイテムの削除と更新機能を追加していきます。

## 親子間通信のレビューと深掘り

ステートのリフトアップを実装したので、この重要な概念をより深く理解し、他の例や図解を通してその仕組みを確認しましょう。親子間通信は、React アプリケーション設計の核心的な概念です。

### 実例による理解：オンライン決済システム

わかりやすい例として、Udemy のようなオンライン学習プラットフォームの決済部分を考えてみましょう。

#### 初期設計での問題

**最初のアプローチ**：

```jsx
function PromotionsComponent() {
  const [coupons, setCoupons] = useState([]); // ローカルステート

  // クーポン追加ロジック
  return (
    <div>
      <input placeholder="クーポンコードを入力" />
      <button>適用</button>
      <ul>
        {coupons.map((coupon) => (
          <li key={coupon.id}>{coupon.code}</li>
        ))}
      </ul>
    </div>
  );
}
```

**発生する問題**：

- `Total` コンポーネントが割引計算をするために`coupons`データが必要
- しかし、`Promotions` と `Total` は兄弟コンポーネント
- React の一方向データフローにより、直接のデータ共有は不可能

```
CheckoutComponent
├── PromotionsComponent (← coupons state はここ)
└── TotalComponent (← coupons data が必要)
```

### ステートのリフトアップによる解決

**解決後の構造**：

```jsx
function CheckoutComponent() {
  const [coupons, setCoupons] = useState([]); // 共通の親に移動

  return (
    <div>
      <PromotionsComponent coupons={coupons} onUpdateCoupons={setCoupons} />
      <TotalComponent coupons={coupons} />
    </div>
  );
}

function PromotionsComponent({ coupons, onUpdateCoupons }) {
  function handleAddCoupon(newCoupon) {
    onUpdateCoupons((prevCoupons) => [...prevCoupons, newCoupon]);
  }

  // UI と イベントハンドリング
}

function TotalComponent({ coupons }) {
  const discount = calculateDiscount(coupons);

  return (
    <div>
      <p>小計: ¥10,000</p>
      <p>割引: -¥{discount}</p>
      <p>合計: ¥{10000 - discount}</p>
    </div>
  );
}
```

### 親子間通信のメカニズム

#### 1. 下向きのデータフロー（Parent → Child）

**通常の props 渡し**：

```jsx
// 親コンポーネント
<ChildComponent data={someData} />;

// 子コンポーネント
function ChildComponent({ data }) {
  return <div>{data}</div>;
}
```

#### 2. 上向きのデータフロー（Child → Parent）

**関数を props として渡す**：

```jsx
// 親コンポーネント
function Parent() {
  const [state, setState] = useState(initialValue);

  return (
    <Child
      currentValue={state}
      onUpdateValue={setState} // setter関数を渡す
    />
  );
}

// 子コンポーネント
function Child({ currentValue, onUpdateValue }) {
  function handleChange(newValue) {
    onUpdateValue(newValue); // 親の状態を更新
  }

  return (
    <button onClick={() => handleChange("new value")}>
      Current: {currentValue}
    </button>
  );
}
```

### 実際のデータフローの分析

**Far Away アプリケーションでの具体例**：

1. **ユーザーアクション**:

   ```
   ユーザーがフォームに入力 → "Passports", 2個
   ```

2. **イベント発生**:

   ```
   Submit イベント → handleSubmit 実行
   ```

3. **データ作成**:

   ```
   newItem = { description: "Passports", quantity: 2, packed: false, id: 123 }
   ```

4. **親への通信**:

   ```
   onAddItems(newItem) → handleAddItems(newItem) (App内で実行)
   ```

5. **ステート更新**:

   ```
   setItems(items => [...items, newItem])
   ```

6. **再レンダリング**:
   ```
   App re-render → PackingList re-render → 新しいItem表示
   ```

### 「逆データフロー」の理解

**なぜ「逆」と呼ばれるのか**：

- React の基本原則は「一方向データフロー」（親 → 子）
- しかし、関数を props として渡すことで、実質的に子 → 親への通信が可能
- これは真の「逆向きフロー」ではなく、巧妙な**ワークアラウンド**

**技術的な仕組み**：

```jsx
// 見た目上は「子から親へ」のデータフロー
onAddItems(newItem); // 子から呼び出し

// 実際は「親から渡された関数」の実行
handleAddItems(newItem); // 親で定義された関数
```

### 設計パターンとしての価値

**ステートのリフトアップの利点**：

1. **データの一元化**: 単一の真実のソース
2. **関心の分離**: 各コンポーネントが適切な責任を持つ
3. **再利用性**: 汎用的なコンポーネント設計
4. **テスタビリティ**: 独立したコンポーネントテストが可能

**現実的な課題**：

- 深いコンポーネント階層では「prop drilling」の問題
- 後のセクションで Context API や state 管理ライブラリで解決

このパターンを理解することで、小〜中規模の React アプリケーションにおける効果的なステート管理の基盤を築くことができます。
