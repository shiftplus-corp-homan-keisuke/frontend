## 暗黙的とは

### 💡言語レベルでの暗黙的処理

プログラミングにおける「暗黙的」とは、**「プログラマーがコードに直接書き示していないにもかかわらず、プログラミング言語やシステムが『気を利かせて』自動的に解釈したり、処理したりすること」**を指します。

「空気を読む」や「言わなくてもわかるでしょ」というニュアンスに近いです。

対義語は**「明示的 (Explicit)」**で、こちらは「プログラマーが『こうしなさい』とコードにハッキリと書き示すこと」を意味します。

### 具体例で見る「暗黙的」

「暗黙的」という概念が最もよく現れるのは、**型の変換**です。

#### 例1：JavaScriptにおける「暗黙的な型変換」

JavaScriptは、文脈に応じて型を自動的に変換してくれる「暗黙的」な動作が多い言語です。

```javascript
let result = "答えは" + 42;
console.log(result); // 出力: "答えは42"
```

このコードでは、プログラマーは数値の`42`を文字列に変換するよう命令していません。しかし、`+`演算子の左辺が文字列`"答えは"`であるため、JavaScriptは「これは文字列の連結だな」と判断し、数値の`42`を**暗黙的に**文字列の`"42"`に変換してから結合しています。

もしこれを**明示的に**書くなら、以下のようになります。

```javascript
// プログラマーが意図をハッキリと示す
let result = "答えは" + String(42);
console.log(result); // 出力: "答えは42"
```
結果は同じですが、後者の方が「数値を文字列に変換している」という意図がコードから明確に読み取れます。

#### 例2：C++やJavaにおける「デフォルトコンストラクタ」

オブジェクト指向言語では、クラスの設計図からオブジェクト（インスタンス）を生成する際に「コンストラクタ」という初期化処理が呼ばれます。

```cpp
class Player {
  // コンストラクタを何も定義しない
};

int main() {
  Player myPlayer; // エラーにならない
  return 0;
}
```

このコードでは、プログラマーは`Player`クラスにコンストラクタを一つも定義していません。しかし、コンパイラが「コンストラクタが一つもないなら、引数なしの空のコンストラクタを**暗黙的に**作っておこう」と気を利かせてくれます。これを**デフォルトコンストラクタ**と呼びます。

### 「暗黙的」のメリットとデメリット

#### メリット
*   **コードが簡潔になる**: いちいち細かい指示を書かなくても済むため、コード量が減り、スッキリ見えることがあります。
*   **記述が楽になる**: 慣れれば直感的に素早くコードを書くことができます。

#### デメリット
*   **予期せぬバグの原因になる**: 「気を利かせたつもり」の自動処理が、プログラマーの意図と違う結果を生むことがあります。
    *   例えば、JavaScriptで`"5" - 2`は**暗黙的に**`5 - 2`と解釈され、数値の`3`になります。しかし、`"5" + 2`は文字列連結と解釈され、文字列の`"52"`になります。この違いを知らないと混乱します。
*   **コードが読みにくくなる**: その言語の「暗黙のルール」を知らない人にとっては、なぜそう動くのかが理解しにくいコードになります。
*   **デバッグが難しくなる**: 見えないところで処理が行われるため、問題が発生したときに原因を特定しにくくなることがあります。

### まとめ

**「暗黙的」とは、コードの裏でよしなにやってくれる自動処理のこと**です。

これはプログラミングを便利にする強力な機能ですが、そのルールを正しく理解していないと、混乱やバグの温床になります。そのため、多くのプログラミングの現場では、**「迷ったら、意図が明確に伝わる『明示的な』コードを書くべきだ」**という考え方が好まれる傾向にあります。



## 📄実装レベルでの暗黙的処理

実装時の「暗黙的」とは、**「コードを一読しただけでは、その処理の『意図』や『背景』、『副作用』が直接読み取れない状態」**を指します。つまり、読み手がコード以外の文脈や前提知識を推測する必要がある、不親切なコードのことです。

コードレビューなどで「暗黙的だ」と指摘される典型的なパターンを、具体例とともに見ていきましょう。

---

### 1. マジックナンバーを使っている

何の説明もなく、コード内に直接書かれた数値や文字列のことです。

**悪い例（暗黙的）:**
```javascript
function canEnter(age) {
  // なぜ「19」？ 20歳以上が条件？ それとも19歳以下？
  if (age < 19) {
    return false;
  }
  // ...
}

// なぜ「2」？ 承認済み？ 却下？
if (user.status === 2) {
  // 承認処理
}
```
*   **なぜ暗黙的か？**: `19` や `2` という数字が何を意味するのか、その数字を知らない人には全く分かりません。仕様書や定義を探しに行く手間が発生します。

**良い例（明示的）:**
```javascript
const ADULT_AGE = 20; // 成人とみなす年齢
function canEnter(age) {
  // 「成人年齢より下なら」という意図が明確
  if (age < ADULT_AGE) {
    return false;
  }
}

const STATUS = {
  PENDING: 1,
  APPROVED: 2, // 承認済み
  REJECTED: 3,
};
// 「ステータスが承認済みなら」という意図が明確
if (user.status === STATUS.APPROVED) {
  // 承認処理
}
```

### 2. 関数名から想像できない処理（副作用）がある

関数名が示す処理以外のことを「黙って」行っている状態です。

**悪い例（暗黙的）:**
```javascript
// 関数名は「ユーザー情報を取得する」だけのように見える
function getUser(userId) {
  const user = db.fetchUser(userId);
  // 暗黙的に最終アクセス日時を更新している！
  db.updateLastAccess(userId);
  return user;
}
```
*   **なぜ暗黙的か？**: `getUser`という名前からは、データを読み取るだけ（Read）だと期待します。しかし、実際にはデータの書き込み（Write）という**副作用**が暗黙的に行われています。これに気づかないと、予期せぬバグの原因になります。

**良い例（明示的）:**
```javascript
// 関数を分割する
function getUser(userId) {
  return db.fetchUser(userId);
}
function updateUserLastAccess(userId) {
  db.updateLastAccess(userId);
}

// または、関数名に全ての処理を記述する
function getUserAndUpdateLastAccess(userId) {
  const user = db.fetchUser(userId);
  db.updateLastAccess(userId);
  return user;
}
```

### 3. 引数の意味が分かりにくい

特に`true`/`false`のような真偽値の引数は、意味が暗黙的になりがちです。

**悪い例（暗黙的）:**
```javascript
// この「true」は何？ 強制的に？ 詳細情報も？
// 呼び出し側だけ見ても意味が全く分からない
const user = createUser('Taro', 'taro@example.com', true);
```
*   **なぜ暗黙的か？**: `true`が何を有効にしているのか、関数の定義を見に行かないと分かりません。

**良い例（明示的）:**
```javascript
// 引数をオブジェクトにすることで、各値の意味を明示する
const user = createUser({
  name: 'Taro',
  email: 'taro@example.com',
  isAdmin: true, // 「管理者として作成」という意図が明確
});

// 関数定義
function createUser({ name, email, isAdmin }) {
  // ...
}
```

### 4. 複雑な三項演算子や一行コード

コードは短くても、処理の流れが追いづらく、結果的に暗黙的になることがあります。

**悪い例（暗黙的）:**
```javascript
// 一見して何をしているのか分かりにくい
const price = user.isVip ? item.price * 0.8 : user.isMember ? item.price * 0.9 : item.price;
```
*   **なぜ暗黙的か？**: 複数の条件が一行に詰め込まれており、処理の優先順位や条件分岐の流れを頭の中で展開する必要があります。

**良い例（明示的）:**
```javascript
// if文で分かりやすく記述する
let price = item.price;
if (user.isVip) {
  price *= 0.8; // VIPは20%割引
} else if (user.isMember) {
  price *= 0.9; // メンバーは10%割引
}
```

### まとめ

「暗黙的なコード」とは、**読み手の努力や推測に依存するコード**のことです。
良いコード、つまり「明示的なコード」とは、以下のような特徴を持ちます。

*   **自己説明的である**: コード自体がその意図を物語っている。
*   **正直である**: 関数名や変数名が処理内容と一致している。
*   **文脈への依存が少ない**: そのコード片だけで完結して理解できる。

コードを書く際には、**「半年後の自分や、このプロジェクトを全く知らない人が、このコードをすんなり読めるだろうか？」**と自問自答することが、「暗黙的」なコードを避けるための良い習慣です。
